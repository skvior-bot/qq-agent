# 上半 · 省钱：钱到底花在哪

## 1. 先看清结构（我们的实测比例）

| 段 | 占比 | 备注 |
| --- | --- | --- |
| 缓存命中的输入 | **36.3%** | 最便宜的一段（73.93 元） |
| 未命中的输入 | **22.3%** | 每次真正新读进去的东西（45.52 元） |
| **输出** | **41.4%** | ★ **最贵的一段**（84.28 元；单价是命中输入的 200 倍） |

> **出处**：三个占比 = 我们**本地全量账本**（161 条会话 / 18,717 步 / 203.74 元）里三段金额之比
> （73.93 ／ 45.52 ／ 84.28 元）；「200 倍」由下面的官方价直接算出（输出 4 ÷ 命中 0.02）。**复算工具见 §7。**

**平台账单（9/1–9/26）＝ 338.09 元 · 28,365 个请求 · 5,748.84M 词元**；
同一台机器上的**本地账本**只有 **203.74 元 / 18,717 步**（≈ 账单的 **60.3%** —— 差额的主因是**被删掉的会话连同日志一起没了**；
**两路统计，别相加**）。

⇒ **反直觉但重要的第一条：输出最贵。** "话多 / 想得多"比"读得多"更烧钱：
我们的推理量约等于**输出量的 57%**（本地账本：推理 48.17 元 ÷ 输出 84.28 元）—— 该降档的活降档，省的是这一块。

## 2. 每个请求都在付的"上下文地板"

实测：**平均每个请求 ≈ 19.8 万词元的上下文**（本地账本，平均/请求）。其中相当一部分是**每一步都要重付的固定开销**
（系统提示 ＋ 工具定义 ＋ 历史）。

⇒ 第二个反直觉结论：**长会话不是"省"，它每一步都在加价。**

## 3. 压缩很贵：一次 ≈ 普通一步的 70 倍

- 实测 12 次压缩的均值：**未缓存输入 ≈ 22 万词元**（≈ 0.24 元/次）；而普通一步 ≈ **0.0034 元**
  —— 这个数**你自己就能算**：一步读 ≈ 16.8 万词元上下文 × 命中价 0.02 元/M。
- ⇒ **压缩阈值必须高于"压缩之后的地板"**：我们实测地板从 **35k 涨到 80~385k**（各会话账本实测）。
  阈值低于地板 ⇒ **每一步都重试压缩** = 压缩风暴，**比不压更贵**。
- 处置：**阈值要设得比"压完以后的常态"还高**；该压的时候一次压到位，别反复蹭。

## 4. 闲时 / 高峰：同一件事差一倍

官方价（元 / M 词元）：

| 时段 | 缓存命中 | 未命中 | 输出 |
| --- | --- | --- | --- |
| **闲时** | 0.02 | 1 | 4 |
| **高峰** | 0.04 | 2 | 8 |

- **高峰 = 工作日 9:00–12:00 与 14:00–18:00**（**不含法定节假日**；调休上班的周末算高峰）。
- 夜间、周末、节假日**全天算闲时**。
- ⇒ **重活排闲时**：同一件事，排对了直接省一半。我们的工具会**自动判定**，不用手算。
- 出处：官方价目 ＋ 我们自己的计价口径（`pricing.mjs`，含法定节假日与调休表）。

## 5. 长会话 vs 归档重开：临界怎么算

- 实测对照：**继续干最后 5 步要 0.0506 元**，而**重开一条再干同样的事只要 0.031 元**。
- 我们用一个比值：`ratio = 长会话已付 ÷ 重开的代价`，**到 45 就强提醒**"该收口了"。
- ★ 上面那两个金额与那个 45，都是我们 `tools\` 里会话卫生工具里的**实测常量**（不是拍的）。
- 为什么长会话会越来越贵：**压缩后的地板本身在膨胀**（实测 **35.5k → 58k**）—— 摘要越厚，每一步都多付缓存读取。
- ⇒ ★ **大任务做完就开新会话**。硬撑不是坚持，是加价。

## 6. 推理档位分级

| 类型 | 例子 | 档位 |
| --- | --- | --- |
| **简单** | 例行自检、跑测试、格式整理、文档同步 | 可以降档 |
| **重要** | 改生产代码、动钱与成本口径、事故处置、架构/产品决策 | 高推理档，**并另开一个同档会话复核** |

# 下半 · 稳定性：我们踩过的真坑（症状 → 根因 → 处置）

## 1. 断档判据（进程冻结 / 系统睡眠）

- **症状**：本机睡 **11 分 50 秒**，醒来发现**少了 2 条消息**（系统事件日志里能读到这一段：`Sleep 01:44:06Z → Wake 01:55:56Z`）。
- **根因**：等待循环拿"墙钟差"当依据；睡眠期间那两拍根本没发生 ⇒ 判不出"断过"。
- **处置**：① 两拍墙钟差 **> 2 拍** ⇒ 判断档（判据原文在我们的桥接实现里：`墙钟差 > 节拍 × 2`）；② 加一道**校时闸** —— 拿**与系统钟无关的心跳**判别，
  否则用户改系统时间会**误报**；③ 判定窗口按**断档时长**放大；④ **只在真缺 ≥ 1 条时才提醒**（夜里空睡不误报）。

## 2. 投递 = 发 ＋ 核实

- **症状**：投出去显示成功，对面**根本没动**。
- **根因**：`accepted:true` 只说明"**收下了**"，不等于"**跑起来了**"；会话列表里的"空闲"**不等于可投递**。
- **处置**：投完**回收据**；别只看单次轮数（轮数会在刚醒时虚低），**≥ 60 秒再采一次**。

## 3. 归档即只读

- **症状**：换了会话之后，消息投给旧 id **静默失效** —— 不报错、也不送达。
- **根因**：归档的会话是**只读历史**，不再收消息；而上下游还在往旧 id 发。
- **处置**：换会话必须 **① 记下新 id ② 主动通知所有相关方**（上下游都要）。我们把这个写成了成文规则：
  **任何会话归档/重开，都要落台账 ＋ 通知，不许"猜"**。

## 4. 单实例信标

- **症状**：两份进程同时活着，共享状态互相覆盖。
- **处置**：**端口归属 = 单实例锁**（谁能绑上那个端口，谁才是正主）；**抢不到锁的复份进程不许写共享 state**。

## 5. 子进程与管道（Windows 上尤其容易踩）

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| `spawn` 带管道 stdio ⇒ **EPERM** | 受限环境**开不了命名管道** | 用**文件 fd**：`stdio: ['ignore', fd, 'ignore']`，跑完读文件 |
| `git archive \| tar -x` 报 `Unrecognized archive format` | **PowerShell 管道会把二进制毁掉** | 先 `-o` 落成文件，再解包 |
| 子进程卡死 / 被 EPIPE 弄死 | `CreateNoWindow` 或 `RedirectStandardOutput` **攥着管道不放** | `Start-Process -WindowStyle Hidden` ＋ **cmd 级文件重定向** |

★ 这三条的共同教训：**在 Windows 上，凡是"跨进程传数据"，能用文件就别用管道。**

## 6. Windows 文本坑（改中文文件的人一定会遇到）

- **PowerShell 5.1 对无 BOM 的 UTF-8 按 ANSI 解码** ⇒ 汉字与后续字节错位配对，**会把换行与引号吞掉** ⇒ 代码直接不可解析。
  ⇒ 改中文文本**别用裸 `Get-Content` / `Set-Content`**：要么用编辑工具，要么显式指定 UTF-8。
- **`.cmd` / `.bat` 必须 CRLF**：我们在仓库根放了 `.gitattributes` **写死行尾**（`.cmd`/`.bat` = CRLF，其余 = LF）
  —— 别依赖每个人自己的 git 配置（实测 `git ls-files --eol`：两个批处理的**索引侧仍是 LF**；这条命令你自己就能复跑）。
- **带 BOM 的启动脚本被编辑器剥掉 BOM** ⇒ 启动直接报错 ⇒ 留一条"**补 BOM**"的自检。

## 7. 交付 / 发布

- **`L1 = 0` 只等于"没有身份真值"，不等于"没有密钥"** —— 密钥/令牌这类字样只进第二层清单 ⇒ **发布前人工过一遍**。
- **扫描工具的"目录档"只吃 `.md`**（`scan-secrets.cjs`）⇒ 它**不是**整包闸（我们被这个误导过：一条命令看着像"全扫过了"，其实只覆盖了几份 markdown）。
- **候选数量守恒**（`export-a.mjs` 的判据）：`进包 ＋ 排除 ＋ 链接 = 候选总数`，对不上就**拒交付**（数量对账对不上时，缺失往往发生在"枚举阶段"，任何对账都看不出来）。
